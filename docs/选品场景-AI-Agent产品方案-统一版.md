## 0. 文档使用说明

- 这不是“概念汇编”，而是“可落地的交付说明书”
- 本文所有设计决策以三个目标为准绳：边界可控、事实真实、输出可用

## 1. 一页纸结论（优先读）

### 1.1 使命与定位

- 使命：为跨境电商卖家提供可信赖的 AI 选品决策助手——在明确能力边界内，基于真实数据给出高质量选品建议，不编造、不越界、不误导
- 定位：不是“全能顾问”，而是“选品决策链专业助手”，以“可控、可溯、可评估”为产品第一性

### 1.2 三大目标（递进关系）

- 目标1：问题边界控制（Scope Control）——先确认“能不能答”
- 目标2：信息真实性保障（Truth Verification）——再确认“答得真不真”
- 目标3：输出质量达标（Quality Assurance）——最后追求“是否值得采纳”

### 1.3 核心方法：Harness Engineering

- 接受“不知道/拒绝”是成功；绝不容忍“编造/越界”
- 通过工程化把 LLM 的不可预测性关进可控流程：输入约束 → 过程校验 → 输出评估

### 1.4 MVP交付策略（最小可信闭环）

- MVP聚焦“双柱场景”：市场分析 + 利润测算，先证明“可信选品”可行
- Guardrails先保底再自动化：MVP阶段用 100% 人工抽检替代自动化审核，随版本逐层加固
- 质量门禁：未过门禁不进入下一阶段（速度服从质量，功能服从信任）

## 2. 成功标准与验收口径

### 2.1 质量指标（长期目标）

- 真实性合规率：100%（红线）
- 问题边界准确率：≥ 95%
- 数据准确率：≥ 85%
- 信息覆盖度：≥ 90%
- 用户满意度：≥ 4.0/5
- 选品采纳率：≥ 50%

### 2.2 阶段里程碑（交付门禁）

- MVP（Week 1-4）：Demo可用，核心链路跑通，Guardrails初版落地，100%人工抽检
- V1.0（Week 5-12）：生产级上线，补齐核心护栏链路，A/B框架就绪，综合质量 ≥ 50%
- V1.5（Week 13-24）：规模化运营，反馈闭环成型，综合质量 75%-85%
- V2.0（Week 25-36）：质量达标，七层防护自动化，综合质量 ≥ 90%

### 2.3 统一验收口径（避免争议）

- 功能验收：端到端用例跑通（包含异常与降级路径）
- 质量验收：抽检+评估集评分达到门禁阈值（第10章）
- 风险验收：红线场景严格拒绝；敏感数据按分级脱敏；全链路可审计（第12章）

## 3. MVP范围与阶段路线图（交付主线）

### 3.1 MVP（Week 1-4）：最小可信产品

#### 3.1.1 做什么（范围）

- 市场分析（基础版）：单品类分析、简化容量估算、趋势方向判断、竞争格局概览
- 利润测算（简化版）：核心成本项拆解（采购+头程+平台费+履约费）、静态测算、敏感因素提示
- Guardrails（基础版）：L1边界判断、L3输入校验、L4真实性校验（基础）、L5溯源包装（基础）、L7质量审核（人工为主）
- 人工抽检：100%人工复核流程与记录模板

#### 3.1.2 不做什么（明确边界）

- 不做竞品监控（需要稳定抓取与风控体系，放到V1.0后）
- 不做选品推荐（依赖前三场景数据口径稳定后再上）
- 不做自动化质量评估（MVP阶段用人工抽检替代，避免误判放过）
- 不做任何法律意见、投资建议、规避合规的灰色方案（红线）

#### 3.1.3 怎么验收（门禁）

- 真实性合规：必须 100%
- 红线拒绝：误放率 0
- 人工抽检：覆盖率 100%，合格率 ≥ 80%
- 延迟：P99 ≤ 15s

### 3.2 V1.0（Week 5-12）：生产级上线

- 场景扩展：补齐竞品监控；选品推荐小范围试点
- Guardrails补齐：L2时效性校验、L6输出生成约束；L7流程标准化
- 数据层补齐：核心数据源接入与数据口径统一
- 质量体系起步：自动评估框架就绪 + 与人工抽检对齐

### 3.3 V1.5（Week 13-24）：规模化运营

- 推荐体系：评分模型与排序引擎，支持偏好学习
- 真实性校验升级：多源交叉验证自动化，冲突处理与置信度分级
- 反馈闭环：用户反馈→归因→优化任务→复测 的闭环跑通

### 3.4 V2.0（Week 25-36）：质量达标与智能化运维

- 七层防护自动化：人工干预率 < 5%
- 可观测性智能化：预测性监控、自动根因分析
- 企业级能力：稳定API、审计追溯、权限与团队协作完善

## 4. 业务场景与输入输出（产品外显形态）

### 4.1 四大核心场景

- 场景1：市场分析（发现机会）
- 场景2：竞品监控（理解竞争）
- 场景3：利润测算（量化收益与风险）
- 场景4：选品推荐（综合排序与决策建议）

### 4.2 场景输入最小集合（缺参策略统一）

统一缺参策略：优先追问澄清（ASK_CLARIFY），其次降级（DEGRADE），最后拒绝（REJECT）；严禁填假值。

- 市场分析：品类/关键词、平台、站点/市场、预算区间（可选）
- 利润测算：采购成本、售价、物流方式、平台、站点/市场、预期销量（可选）
- 竞品监控：竞品ASIN/链接、监控维度、时间范围
- 选品推荐：预算范围、品类偏好、风险承受等级、筛选条件

## 5. Harness Engineering 总体框架（七维 → 七层防护）

### 5.1 为什么需要 Harness Engineering（选品场景硬约束）

- 错误数据的代价极高：错误销量/费率/合规信息会直接造成资金损失与合规风险
- LLM 的“语义级故障”传统监控发现不了，必须引入语义层护栏与评估

### 5.2 七维（理念框架）

- 维度1：问题边界控制（Scope Control）
- 维度2：安全护栏（Guardrails）
- 维度3：工作流编排（Workflow Orchestration）
- 维度4：多Agent协作（Multi-Agent Collaboration）
- 维度5：权限控制（Access Control）
- 维度6：可观测性（Observability）
- 维度7：评估体系（Evaluation Framework）

### 5.3 七层（执行框架）

七维是“设计语言”，七层是“运行时执行框架”：用 L1-L7 把风险前移到每个关键节点。

## 6. 系统设计（四层架构 + 多Agent + 数据层）

### 6.1 四层分离架构

- 交互层：对话界面/管理后台/开放API，统一接入、鉴权、限流、输出渲染
- 编排层：主控Agent（Orchestrator）+ 工作流状态机 + Context Store
- 防护层：边界控制 + 七层防护执行 + 质量保障
- 数据层：数据源接入/治理/存储/服务化，支撑全链路溯源与审计

### 6.2 多Agent体系（1+N）

- 主控Agent：听-拆-派-聚-说（不直接做专业分析）
- 专业Agent：市场分析（MA）、竞品分析（CA）、利润测算（PM）、合规检查（CC）

### 6.3 数据层关键原则

- 分级接入（Tier 1/2/3/Prohibited），禁止源触发告警
- 溯源贯穿：每个关键数据点必须有来源、时间、版本、置信度
- 降级策略：数据不可用时宁可降级/拒绝，不可编造

## 7. Guardrails 七层防护（L1-L7）与统一处置语义

### 7.1 七层定义

- L1 边界判断：意图分类、核心圈/扩展圈/红线判定，红线严格拒绝
- L2 时效性校验：识别是否需要实时数据，触发刷新与缓存策略
- L3 输入校验：参数完整性、范围、注入风险、格式合法性
- L4 真实性校验：来源分级、多源交叉验证、冲突处理、可信度评分
- L5 溯源包装：为关键数据附加来源、时间、版本、置信度
- L6 输出生成：在约束下生成，保证结构、引用、免责声明一致
- L7 质量审核：一致性检查、幻觉检测、合规检查；必要时拦截/重写/人工介入

### 7.2 统一处置语义（全链路通用）

- ALLOW：允许进入下一步
- ALLOW_WITH_CONSTRAINTS：允许，但必须带约束（例如只输出历史趋势不做预测）
- ASK_CLARIFY：追问澄清，补参后继续
- REJECT：拒绝，并给出原因码与替代建议
- DEGRADE：降级输出（部分结果 + 缺失声明 + 不确定性标注）

## 8. 运行时确定性机制（上下文组装/记忆/压缩/编排/并行/权限/Hook）

本章回答一个核心问题：当上下文变长、任务变复杂、并发变多时，如何避免“靠Prompt让模型记住”的脆弱方案，让系统以确定性机制持续可控运行。

### 8.1 作用域上下文组装（Scoped Context Assembly）

目标：按需加载、拒绝臃肿、可审计可复现。

- 上下文来源分层：项目级指令 / 场景级指令 / 模块级指令 / 角色级指令 / 任务facts
- 动态加载顺序（越具体优先级越高）：Repo层 → 场景层 → 任务层 → 会话层
- 合并规则：更具体者优先；任何冲突向保守策略倾斜；装配清单必须可审计（记录片段、版本、时间）

### 8.2 记忆分层（Tiered Memory）

目标：让“该记住的记住、该忘掉的忘掉”，并防止记忆污染。

- 运行时上下文：单次调用的输入与约束
- 会话记忆：多轮对话的目标与关键参数
- 任务记忆：任务DAG的中间产物、溯源数据点、校验与质量结果
- 长期记忆：稳定偏好、组织级规则、经验证口径、评估集样本

写入规则：只有可溯源可复核的事实才允许升级到任务/长期记忆；低可信信息不得升级；红线相关只记录最小审计字段并脱敏。

### 8.3 睡眠记忆巩固（Dream Consolidation）

目标：把会话资产沉淀成可复用的确定性资产，而不是留在上下文里慢慢遗忘。

- 触发：任务完成 / 有证据的失败 / 用户反馈 / 周期性归档
- 产物：会话摘要、可复用facts、评估样本、规则改进建议

### 8.4 渐进式上下文压缩（Progressive Context Compaction）

目标：压缩表达，不压缩事实。

- L0 原始对话（短期保留）
- L1 轮次摘要（目标/参数/结论/引用）
- L2 会话摘要（合并多轮，保留冲突与未决点）
- L3 任务fact表（结构化facts + citations + confidence）

触发：上下文达到阈值 / 进入新任务版本 / 并行合并前。

### 8.5 工作流与编排（Explore / Plan / Act）

目标：用状态门禁限制权限与副作用，避免误写、误调用高风险工具。

- Explore：只读探索（读/搜/列目录/检索），禁止写入与外部副作用
- Plan：只读规划（形成计划、校验、风险评估），禁止写入与外部副作用
- Act：执行态（允许写入、外部工具调用、数据刷新与Hook触发）

### 8.6 Fork-Join 并行（无依赖任务并发）

目标：并行提升速度，但不牺牲一致性与可追溯。

- 并行原则：只对无依赖任务并行；共享输入不共享可写对象
- 写冲突控制：对象级独占或版本化写入，禁止直接覆盖
- Join合并顺序：事实 → 推理 → 表达；冲突进入 L4 交叉验证；仍不确定则输出不确定性并建议人工核实

### 8.7 工具与权限设计（精准赋权）

目标：默认极简工具集（<20），按需激活，步骤结束回收，所有激活可审计。

- 默认：只读查询、校验、溯源、观测类
- 激活触发：进入Act态/用户明确要求实时刷新/角色为Admin
- 最小化范围：仅本次任务/本次步骤生效

### 8.8 生命周期自动化（事件流Hook）

目标：独立于会话的确定性运行，摆脱“上下文压力导致遗忘”。

最小事件集合：

- on_request_received
- on_scope_decided
- on_missing_input_detected
- on_data_fetch_started / on_data_fetch_completed
- on_truth_verified / on_truth_failed
- on_output_generated
- on_quality_passed / on_quality_blocked
- on_user_feedback_received
- on_task_completed

每个事件必须定义必做动作（记录、校验、拦截/降级、沉淀样本），并写入统一审计字段（见第9章）。

## 9. 契约与接口（统一字段、错误码、溯源规范、协作协议）

本章的目的：让系统各模块以同一语言协作，确保“可编排、可测、可观测、可审计、可回放”。

### 9.1 统一身份与追踪字段（必带）

- request_id：单次请求唯一ID
- session_id：会话ID（多轮共享）
- task_id：任务DAG实例ID
- task_version：任务版本（用户修改参数/重新分析时递增）
- actor_role：ADMIN / ANALYST / VIEWER
- tenant_id：租户/组织（如有）

### 9.2 处置语义（Disposition，统一枚举）

- ALLOW / ALLOW_WITH_CONSTRAINTS / ASK_CLARIFY / REJECT / DEGRADE

### 9.3 L1 边界控制输入输出契约（摘要）

输入：

- user_query
- context_summary（可为空）
- actor_role
- known_constraints

输出：

- scenario（命中场景或 OUT_OF_SCOPE）
- disposition
- intent_label
- confidence（0-1）
- risk_level（L1_CRITICAL/L2_HIGH/L3_MEDIUM/L4_LOW/L5_INFO）
- constraints（若 ALLOW_WITH_CONSTRAINTS）
- reject_reason_code（若 REJECT）
- user_facing_message_template_id

### 9.4 七层输出统一结构（GuardrailResult）

- layer（L1-L7）
- disposition
- summary
- evidence（规则/来源/校验结果）
- errors（含 error_code）
- metrics（耗时、命中规则等）

### 9.5 溯源包装字段规范（L5必做）

每条影响结论的数据点必须携带：

- data_point_id
- value
- unit
- observed_at
- valid_until（如适用）
- source（API/知识库/用户输入/第三方）
- source_ref（URL/文档版本/接口名+版本）
- confidence（0-1）
- processing_trace

### 9.6 错误码最小集合

- E_SCOPE_REDLINE：红线越界
- E_AUTH_FORBIDDEN：权限不足
- E_INPUT_MISSING：关键输入缺失
- E_DATA_UNAVAILABLE：数据源不可用
- E_DATA_CONFLICT：多源数据冲突
- E_TRUTH_UNVERIFIED：真实性无法验证
- E_QUALITY_BLOCKED：质量审核拦截

### 9.7 多Agent协作协议（摘要）

- 主控Agent只负责调度与聚合，不直接生成专业事实
- 专业Agent输出必须结构化并携带 citations、confidence、limitations
- 冲突仲裁：优先呈现分歧+证据；收益高 vs 风险高时风险优先；数据冲突进入 L4 交叉验证

## 10. MVP落地清单（不做清单、用例、抽检与评估集、发布门禁）

### 10.1 MVP必须交付

- 场景：市场分析（基础）+ 利润测算（简化）
- Guardrails：L1/L3/L4/L5 + L7人工抽检
- 记录：每次交互必须产生日志、溯源、处置结果

### 10.2 MVP不做（再次明确）

- 竞品监控、选品推荐、自动化质量评估
- 法律意见、投资建议、规避合规灰色方案
- 非授权私有数据的抓取/推断/泄露

### 10.3 MVP端到端用例（最小集合）

- 市场分析：输入品类/平台/市场，输出结构化报告（含来源与时间）
- 利润测算：输入成本/售价/平台/市场，输出成本拆解表（公式可解释）
- 缺参追问：缺关键字段触发 ASK_CLARIFY，补参后继续
- 数据不可用降级：触发 DEGRADE（框架+缺失声明），不编造
- 红线拒绝：触发 REJECT，原因码正确且话术合规

### 10.4 人工抽检（MVP强制）

- 抽检比例：100%
- 复核角色：产品经理 + 数据/研发（双人复核）
- 记录字段：request_id、场景、处置语义、关键数据点、问题类型、是否阻断、修复建议

### 10.5 MVP评估集（建议最小集）

- 边界判定评估集：≥ 200 条（核心圈/扩展圈/红线混合，人工标注真值）
- 市场分析评估集：≥ 20 个已知品类（粗标签对比）
- 利润测算评估集：≥ 20 个真实SKU历史样本（允许误差区间但必须可解释）

## 11. 可观测性与审计追溯（三层观测 + 回放）

- 系统层：可用性、延迟、错误率、资源使用
- 业务层：任务DAG步骤成功率、工具调用、数据流转与缓存命中
- 语义层：幻觉率、边界漏判率、质量评分分布、用户满意度与采纳率

审计追溯要求：

- 任意 request_id 可回放：当时输入、数据状态、规则版本、模型版本、处置链路、输出与溯源
- 观测数据脱敏：敏感字段按分级展示与存储

## 12. 合规、安全与风险边界

### 12.1 红线（必须严格拒绝）

- 投资建议、法律意见、规避关税/平台规则的灰色方案
- 个人隐私、商业机密、非授权私有数据

### 12.2 数据分级与访问控制（概要）

- 数据分级（S1-S4）+ 角色分级（Admin/Analyst/Viewer）+ 场景分级（四场景）
- 原则：最小必要、最小权限、默认拒绝、全程审计

### 12.3 主要风险与应对

- 幻觉与越界：L1-L7 + 人工抽检起步 + 评估集门禁 + Hook拦截
- 数据源波动：分级接入 + 熔断降级 + 多源交叉验证 + 版本化缓存
- 合规风险：红线拒绝 + 合规Agent + 输出声明与溯源
- 质量债务：质量门禁 + 指标看板 + 周期性复盘 + 样本沉淀

## 13. 总结

这份统一版把三件事合成一条可交付主线：

- 产品交付：MVP范围与门禁明确，不做清单明确，验收口径明确
- 运行时可靠：七层防护 + 统一处置语义，让错误在系统内被拦截、降级或拒绝
- 系统确定性：Scoped Context Assembly + 记忆分层 + 渐进压缩 + Explore/Plan/Act门禁 + Fork-Join合并 + 生命周期Hook，把关键动作从“模型记忆”迁移到“事件流确定性机制”
