## 二、Java 控制面开发需求

### 2.1 P0 — 核心链路修复（1d）

#### 2.1.1 确认 RestTemplate Bean 配置

**现状**：`CrobExecutorClientImpl` 注入了 `RestTemplate`，需确认 Spring 容器中是否有 Bean 定义。

**需求**：
- 若缺失，在 `Crob-server` 的配置类中声明 `RestTemplate` Bean（含超时 30s、连接池）
- 若已存在，验证超时/重试配置是否合理

**验收**：启动不报注入错误，HTTP 调用正常。

#### 2.1.2 修复 Python 事件 fire-and-forget 隐患

**现状**：Python `_post_attempt_event` 不等待 HTTP 响应。若事件丢失，Java 状态机永远等不到 ATTEMPT_SUCCEEDED/FAILED，任务卡在 RUNNING 直到超时扫描（5 分钟）。

**需求（Java 侧兜底）**：
- 在 `scanTimeoutAttempts()` 中增加"无事件超时"判定：如果 attempt 处于 RUNNING 且 2 分钟内无任何新事件（非仅 HEARTBEAT），标记为 E_EXECUTOR_LOST
- 增加日志告警：当同一 executor 连续出现 E_EXECUTOR_LOST 时打印 WARN

**验收**：Python 进程被 kill 后，2 分钟内 Java 自动将 attempt 标记为 FAILED(E_EXECUTOR_LOST)。

### 2.2 P1 — 门禁与校验增强（2d）

#### 2.2.1 L3 输入合法性校验（数值范围）

**现状**：Java `validate()` 只做了必填字段检查和 "OTHER" 拒绝，没有数值范围校验。产品方案 MVP 要求 L3 必须校验参数合法范围。

**需求**：
- `validate()` 方法增加以下校验规则：

| 场景 | 字段 | 校验规则 | 失败动作 |
|------|------|---------|---------|
| PROFIT_MODEL | cost_fen | > 0，整数 | missingFields 中加入 cost_fen，提示"成本必须大于 0" |
| PROFIT_MODEL | price_fen | > 0，整数 | 同上 |
| PROFIT_MODEL | shipping_mode | 从允许列表中选择 | 同 OTHER 拒绝逻辑 |
| MARKET_ANALYSIS | platform | 从 [amazon, temu, tiktok_shop] 中选择 | rejectReason = "PLATFORM_NOT_SUPPORTED" |
| MARKET_ANALYSIS | market | 从 [us, uk, de, jp, sea] 中选择 | rejectReason = "MARKET_NOT_SUPPORTED" |
| ALL | prompt | 长度 ≤ 2000 字符 | rejectReason = "PROMPT_TOO_LONG" |

**验收**：发送 cost_fen=0 的 PROFIT_MODEL 请求 → WAITING_INPUT + missingFields 含 cost_fen。

#### 2.2.2 负利润确认逻辑完善

**现状**：Java 侧 `validate()` 中 price < cost 时要求 `confirm_negative_profit` 字段，但当前实现只检查字段存在性，未区分"用户确认继续"vs"用户放弃"。

**需求**：
- `confirm_negative_profit` 值为 `"YES_CONTINUE"` 时放行（REJECTED→QUEUED）
- 值为 `"NO_ABORT"` 时 REJECTED
- 缺此字段时保持 WAITING_INPUT，missingFields 中包含明确提示"当前测算为负利润，确认继续请输入 confirm_negative_profit=YES_CONTINUE"

**验收**：price < cost → WAITING_INPUT → 补参 YES_CONTINUE → QUEUED。

#### 2.2.3 增加 CANCELLING 中间态

**现状**：cancel 直接从 RUNNING → CANCELLED，无中间态。

**需求**：
- 新增状态 `CANCELLING`（Java 和 Python 常量同步）
- cancel 操作：task + attempt → CANCELLING → 设置 Redis cancel 标志
- Python 检测到 cancel 标志后上报 ATTEMPT_CANCELLED
- Java 收到 ATTEMPT_CANCELLED → 更新 task + attempt → CANCELLED
- 超时兜底：CANCELLING 状态超过 60s → 强制 CANCELLED

**验收**：cancel 后 SSE 流中看到 CANCELLING → CANCELLED 状态流转。

**六种模版类型说明**：

| 模版类型 | 作用 | 对应概念 | 示例 |
|---------|------|---------|------|
| **AGENT** | 系统级指令，定义 Agent 是什么、能做什么、不能做什么 | 类似 CLAUDE.md 的角色定义 | "你是一个跨境电商选品专家，专注于市场分析和利润测算…" |
| **SOUL** | 人格与风格定义，语调、表达偏好、回复风格 | 类似 Character Card | "你的语调：专业但平易近人，用数据说话但不说教。当你不知道时坦诚告知…" |
| **SCENARIO** | 场景执行流程与步骤定义，替代硬编码的 `_run_market_analysis` 等 | 类似 workflow/pipeline 定义 | 定义 MA_01→MA_05 步骤及每步的 prompt 片段 |
| **TOOLS** | 可用工具声明，工具名称、描述、参数 schema | 类似 function calling 定义 | "search_market_data: 搜索市场数据，参数：platform, market, keyword" |
| **GUARDRAILS** | 护栏规则，L1-L7 的规则定义 | 安全策略模版 | 红线关键词列表、Tier 分级规则、输出校验规则 |
| **OUTPUT** | 输出格式定义，报告结构、字段要求 | 结构化输出 schema | 报告必须包含：关键结论、数据证据表、风险与限制、建议动作 |

**模版变量语法**：

```
{{variable_name}}              — 简单变量替换
{{variable_name:default}}      — 带默认值
{{#if variable_name}}...{{/if}} — 条件块（V1.5）
```

## 三、Python 执行面开发需求

### 3.1 P0 — 事件上报可靠性（0.5d）

#### 3.1.1 post_internal 增加重试与超时

**现状**：`java_client.py` 的 `post_internal` 不等待响应。

**需求**：
- 增加 timeout=10s
- 增加重试：瞬时错误（429/503/504/连接超时）重试 1 次
- 非瞬时错误（4xx 签名错误等）不重试，直接 log error
- 区分"事件发送失败"和"业务失败"，事件失败记录到本地日志但不影响主流程

**验收**：Java 临时不可用时，Python 重试 1 次后继续执行，事件不丢失。

### 3.2 P1 — Guardrails 对齐 MVP 标准（2d）

#### 3.2.1 L3 输入数值校验

**需求**（Python 侧二次校验，防御深度）：

- `_run_profit_model` 进入后立即校验 cost_fen > 0、price_fen > 0
- `_run_market_analysis` 校验 platform/market 在允许列表中
- 校验失败 → raise RuntimeError("E_INPUT_INVALID: <具体原因>")

#### 3.2.2 L4 数据来源标注覆盖全部场景

**现状**：仅 MARKET_ANALYSIS 有来源标注。产品方案 MVP 要求"所有输出数据标注来源"。

**需求**：

**PROFIT_MODEL 场景**：
- 在计算完成后构造 data_point：
```python
data_points = [
    {
        "data_point_id": f"profit_model/{platform}/{market}",
        "source": "user_input",
        "observed_at": datetime.utcnow().isoformat(),
        "confidence": 0.9,  # 用户输入数据假设为高可信
    },
    {
        "data_point_id": "rate_profile/default",
        "source": "system_default",
        "observed_at": "2026-06-02",
        "confidence": 0.5,  # 默认费率低可信
        "note": "当前使用系统默认费率，未加载实时费率表"
    }
]
```

**CHAT 场景**：
- 标注为 `confidence: 0.3, source: "llm_knowledge"`，明确告知用户"以下信息基于模型训练数据，未经过实时验证"

**通用要求**：
- 所有场景的 LLM prompt 追加"请在报告末尾列出数据来源与置信度"指令

#### 3.2.3 利润测算公式透明化

**需求**：
- `_run_profit_model` 生成的 prompt 必须包含完整计算公式展示
- 不只是给结果，要展示计算过程：
```
成本构成明细：
- 采购成本：{cost_fen} 分
- 售价：{price_fen} 分  
- 毛利润：{price_fen - cost_fen} 分
- 毛利率：{(price_fen - cost_fen) / price_fen * 100:.1f}%

注意：当前版本仅计算采购成本与售价差额，平台佣金、FBA费用、物流费用、广告费用等尚未计入。
实际净利润可能显著低于此毛利润。完整费率模型将在后续版本中支持。
```

#### 3.2.4 不确定性表达注入

**需求**：在 LLM 的 system prompt（AGENT 模版）中注入不确定性表达规则：

```
# 不确定性表达规则
- 对于估算数据，使用区间而非单点值（如"月销量估算：8万-15万件"而非"月销量12万件"）
- 对于非官方数据，标注置信度等级
- 对于无法确认的信息，明确说"该数据我暂时无法确认"
- 禁止使用以下模糊词汇：大概、可能、据说、应该、预计（除非附带明确的数据依据）
```

#### 3.3.2 执行器重构：动态编排

**修改文件**：`app/executor.py`

**核心变更**：将硬编码的 `_run_market_analysis` / `_run_profit_model` / `_run_chat` 替换为通用执行器：

```python
def run_attempt(task_id, attempt_id, scenario, inputs, effective_constraints, workspace_config=None):
    # ... lock + heartbeat 不变 ...
    
    # 使用 workspace_config 中的配置替换硬编码逻辑
    if workspace_config:
        steps = workspace_config.get("scenario_steps", [])
        agent_instruction = workspace_config.get("agent_instruction", "")
        soul_prompt = workspace_config.get("soul_prompt", "")
        guardrails = workspace_config.get("guardrails_config", {})
        output_schema = workspace_config.get("output_schema", {})
    else:
        # fallback: 使用代码内置默认配置（兼容旧任务）
        steps, agent_instruction, soul_prompt, guardrails, output_schema = _get_default_config(scenario)
    
    # L1 使用 guardrails 配置
    _l1_check_from_config(task_id, attempt_id, seq, scenario, inputs, guardrails)
    
    # 动态执行步骤流程
    report_md, usage = _run_scenario_steps(
        task_id, attempt_id, steps, inputs, seq, r,
        agent_instruction, soul_prompt, guardrails, output_schema
    )
```

**`_run_scenario_steps` 通用步骤执行器**：

```python
def _run_scenario_steps(task_id, attempt_id, steps, inputs, seq, r,
                        agent_instruction, soul_prompt, guardrails, output_schema):
    """
    通用场景步骤执行器，根据 steps 定义动态执行。
    
    steps 格式：
    [
        {"step": "MA_01_VALIDATE_INPUT", "type": "validate", "rules": {...}},
        {"step": "MA_02_BUILD_QUERY_PLAN", "type": "prompt", "template": "..."},
        {"step": "MA_03_FETCH_DATA", "type": "fetch", "source": "..."},
        ...
    ]
    
    step type 支持：
    - validate: 输入校验
    - prompt: 构建并发送 LLM prompt
    - fetch: 获取外部数据
    - compute: 本地计算
    - verify: 真实性校验
    """
    variables = dict(inputs)
    context = {}  # 步骤间共享上下文
    
    for step_def in steps:
        _check_cancel(r, attempt_id)
        step_name = step_def["step"]
        step_type = step_def.get("type", "prompt")
        
        _post_attempt_event(task_id, attempt_id, seq, "STEP_CHANGED", {"step": step_name})
        
        if step_type == "validate":
            _execute_validate_step(step_def, variables)
        elif step_type == "fetch":
            result = _execute_fetch_step(step_def, variables, context)
            context[step_name] = result
        elif step_type == "compute":
            result = _execute_compute_step(step_def, variables, context)
            context[step_name] = result
        elif step_type == "verify":
            _execute_verify_step(step_def, variables, context)
        elif step_type == "prompt":
            # 使用模版引擎构建 prompt
            system_prompt = build_system_prompt_from_config(agent_instruction, soul_prompt)
            user_prompt = render_template(step_def.get("template", ""), {**variables, **context})
            messages = [
                {"role": "system", "content": system_prompt},
                {"role": "user", "content": user_prompt},
            ]
            report_md, usage = _llm_generate_report(task_id, attempt_id, messages, seq, r)
            context["report_md"] = report_md
            context["usage"] = usage
    
    return context.get("report_md", ""), context.get("usage", {})
```
